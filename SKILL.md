## Agent roles reference

Each task's full role definition (ground rules, responsibilities, workflow, output format) lives in its own reference file — read one in full before enqueuing that task, since each runs as an isolated prompt that never sees this document:

- [`domain-researcher`](references/domain-researcher.md) — studies how a named domain is actually implemented in this project's own source code, including a dependency graph between the domain's found concerns.
- [`public-api-writer`](references/public-api-writer.md) — documents each source file's public API surface in full detail, plus any API specification files (OpenAPI, GraphQL, Protobuf, AsyncAPI); splits its own work across 2-4 sub-workers by folder for a large enough scope.
- [`git-explorer`](references/git-explorer.md) — extracts the project's full git commit history and indexes the ticket IDs referenced in commit messages; its `ticket.md` output is the required input for a later `ticket-researcher` run.
- [`ticket-researcher`](references/ticket-researcher.md) — enriches the ticket IDs `git-explorer` found with their real Jira content and linked Confluence docs; requires `git-explorer`'s `ticket.md` to already exist, so it can only be enqueued after `git-explorer`'s task completes.
- [`ext-lib-inspector`](references/ext-lib-inspector.md) — catalogs a project's direct external/third-party dependencies across every manifest found, with a one-sentence summary of what each one is for.
- [`logic-describer`](references/logic-describer.md) — takes a list of file paths as input and, for each one, writes a line-anchored logic walkthrough plus its Level 1 internal dependencies and class-to-class edges; enqueued once per 10-file chunk of the project's file list, never with the whole project in one task.

## Workflow

1. **Sanity-check `.gitignore` before anything else reads the tree.** Enumerate every `.gitignore` in the project — root and nested (e.g. `find . -name .gitignore -not -path '*/.git/*'`) — and inspect them together, not one file in isolation:
   - **Conflicts**: a nested `.gitignore` that re-ignores or un-ignores (`!pattern`) a path the root file already governs, or two rules anywhere in the tree that contradict each other for the same path.
   - **Consistency**: overly broad patterns (a bare `*`, `**`, or a root-level pattern that also swallows a directory the project actually needs tracked), and duplicate/redundant rules repeated across files.
   - **Verify against reality, don't just read the patterns.** Run `git ls-files --cached --others --exclude-standard` and confirm the result is non-trivial and includes what you'd expect — the project's own manifest, its README, an obvious source directory. For any path you're unsure about, `git check-ignore -v <path>` names the exact rule (file + line) responsible for it.
   - If the tracked/untracked count is zero or suspiciously small, an expected file is missing, or you find a genuine conflict, **stop and flag the `.gitignore` configuration to the user** rather than continuing — everything this skill does downstream depends on that file list being accurate.
2. **Build the full source file list.** Run `git ls-files --cached --others --exclude-standard` (already sanity-checked as trustworthy in step 1) and write the result, one file path per line, to `.cache/recuperate/source-files.txt` — this is the single gitignore-respecting file list every task below scopes itself against, so no task re-derives it independently.
3. **Dispatch the task queue via `team_create` + `task_create`.** Create the team once with `team_create`, then spawn the teammate agents that will actually claim and run tasks under it — `team_create` alone produces the team's container and task list, not workers; without at least one spawned teammate, nothing enqueued afterward has anyone to claim it. Only once teammates exist, enqueue every unit of work as a task under the team with `task_create` in the same batch — this is what makes them a queue rather than a sequence of one-off calls: none is started before or staggered after another. For each task, read its role's reference file in full (see Agent roles reference above) and use that complete content as the task prompt, appending the concrete scope it needs.
   - **Terminology: every "Enqueue `<role>`" instruction in the steps below means exactly this — call `task_create` for that task, under the team created here with `team_create`.** "Enqueue" is never a separate mechanism, a chat message, or a plain `Agent` tool call; it always resolves to this one `team_create` + `task_create` pair.
   - **A newly created task starts in `pending` status, not running — an available teammate claiming it is what actually starts execution, and `task_create` itself doesn't guarantee that happens immediately.** None of the crawler tasks this skill enqueues ever use `task_create`'s dependency field on each other (they're independent, so nothing is gated waiting on another task's completion within the same batch) — the only sequencing in this skill is the deliberate later dispatch of `ticket-researcher` in step 9, done by enqueuing it in a separate call after `git-explorer`'s signal, not via a dependency field. A task sitting in `pending` longer than expected, despite teammates being free, isn't something to route around — treat it the same as a slow-running task under the "no time limit" rule below and keep waiting; it is not evidence the queue is broken.
   - **Right after each `task_create` call, check whether a teammate is currently free and, if so, try to start that task immediately** — the same claim/assign action used for a stuck pending task (see below), just applied at enqueue time instead of only after a later completion signal. When every teammate is already busy, leave the new task pending; it'll get picked up either by the normal claim process or by the check that runs on the next completion signal.
   - Each task gets its own disjoint output path so tasks never race each other on a shared file, regardless of run order or timing.
   - Tasks don't talk to each other or hand back a summary in chat — each one reports only a completion signal (success) or a plain statement of why it couldn't finish (genuine hard failure). Retrieve actual results by reading each task's output path directly, not from what it said.
   - **Wait for every task's completion signal before treating the queue as drained.** A queue with even one task still pending or one that reported partial output is not a valid base for the next step — there's no time limit on this wait, and a slow task is progress, not a hang. A task interrupted partway through has not produced valid output; re-run it to completion rather than build on what it managed before being cut off.
   - **On every task's completion signal, check the queue for any tasks still stuck in `pending` and try to get them started.** A finished task frees up a teammate slot, and that's exactly the moment a still-pending task should become claimable — but claiming isn't always automatic, so after each `JOB DONE` (or failure), list the team's tasks and, for any genuinely idle-but-pending one, explicitly try to move it forward (re-assign it to the now-free teammate, or whatever claim/nudge action the runtime provides) rather than only ever waiting passively.
4. **Enqueue `domain-researcher` for each domain to study.** Determine the domain(s) to research from the project's own description (README, package/manifest) — never ask the user first; if no domain is clearly named, pick the most reasonable candidate(s) yourself (most prominent directory/module grouping, the subject of the README) and let `domain-researcher`'s own Scope section record that assumption. Enqueue one `domain-researcher` task per domain through the queue mechanism from step 3, each scoped to its own domain name.
5. **Enqueue `public-api-writer` for the whole project.** Unlike `domain-researcher`, this role takes no per-domain scope — enqueue a single top-level task through the queue mechanism from step 3, covering the full project; the role's own workflow decides internally whether to split further across its own sub-workers.
6. **Enqueue `git-explorer` for the whole project.** Also no per-domain scope — enqueue a single top-level task through the queue mechanism from step 3, covering the full project's git history. Its `ticket.md` output is a hard prerequisite for a later `ticket-researcher` task, so `ticket-researcher` must be enqueued only after this task's completion signal, never in the same batch as this step.
7. **Enqueue `ext-lib-inspector` for the whole project.** Also no per-domain scope and no dependency on any other task's output — enqueue a single top-level task through the queue mechanism from step 3, alongside steps 4-6, covering the full project's manifests.
8. **Split `.cache/recuperate/source-files.txt` into 10-file chunks and enqueue one `logic-describer` task per chunk.** Read the file list from step 2 and partition it into consecutive groups of 10 paths each (the last group holding the remainder, whatever size that leaves it). For each chunk, enqueue a `logic-describer` task through the queue mechanism from step 3, passing that chunk's file paths inline in the task prompt as its scope — never the whole `source-files.txt` path as a single task's scope, and never more than 10 files to one task. These tasks have no dependency on any other task's output, so they run alongside steps 4-7.
9. **Once `git-explorer`'s task from step 6 reports its completion signal, enqueue `ticket-researcher`.** This is a separate, later dispatch through the same queue mechanism from step 3 — never batched alongside step 6, since `ticket-researcher` reads `git-explorer`'s `ticket.md` as its required input and would otherwise race a still-running or not-yet-started `git-explorer` task. If `git-explorer`'s task reported a hard failure instead of `JOB DONE` (no `ticket.md` produced), skip enqueuing `ticket-researcher` and note why in the final report.
