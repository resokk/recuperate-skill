## Agent roles reference

Each task's full role definition (ground rules, responsibilities, workflow, output format) lives in its own reference file — read one in full before enqueuing that task, since each runs as an isolated prompt that never sees this document:

- [`domain-researcher`](references/domain-researcher.md) — studies how a named domain is actually implemented in this project's own source code, including a dependency graph between the domain's found concerns.
- [`public-api-writer`](references/public-api-writer.md) — documents each source file's public API surface in full detail, plus any API specification files (OpenAPI, GraphQL, Protobuf, AsyncAPI); splits its own work across 2-4 sub-workers by folder for a large enough scope.
- [`git-explorer`](references/git-explorer.md) — extracts the project's full git commit history and indexes the ticket IDs referenced in commit messages; its `ticket.md` output is the required input for a later `ticket-researcher` run.
- [`ticket-researcher`](references/ticket-researcher.md) — takes a list of ticket IDs as input and enriches each with its real Jira content and linked Confluence docs; requires `git-explorer`'s `ticket.md` to already exist, so it can only be enqueued after `git-explorer`'s task completes, and then once per 50-ticket batch, never with the whole ticket list in one task.
- [`ext-lib-inspector`](references/ext-lib-inspector.md) — catalogs a project's direct external/third-party dependencies across every manifest found, with a one-sentence summary of what each one is for.
- [`logic-describer`](references/logic-describer.md) — takes a list of file paths as input and, for each one, writes a line-anchored logic walkthrough plus its Level 1 internal dependencies and class-to-class edges; enqueued once per 50-file chunk of the project's file list, never with the whole project in one task.

## Workflow

1. **Sanity-check `.gitignore` before anything else reads the tree.** Enumerate every `.gitignore` in the project — root and nested (e.g. `find . -name .gitignore -not -path '*/.git/*'`) — and inspect them together, not one file in isolation:
   - **Conflicts**: a nested `.gitignore` that re-ignores or un-ignores (`!pattern`) a path the root file already governs, or two rules anywhere in the tree that contradict each other for the same path.
   - **Consistency**: overly broad patterns (a bare `*`, `**`, or a root-level pattern that also swallows a directory the project actually needs tracked), and duplicate/redundant rules repeated across files.
   - **Verify against reality, don't just read the patterns.** Run `git ls-files --cached --others --exclude-standard` and confirm the result is non-trivial and includes what you'd expect — the project's own manifest, its README, an obvious source directory. For any path you're unsure about, `git check-ignore -v <path>` names the exact rule (file + line) responsible for it.
   - If the tracked/untracked count is zero or suspiciously small, an expected file is missing, or you find a genuine conflict, **stop and flag the `.gitignore` configuration to the user** rather than continuing — everything this skill does downstream depends on that file list being accurate.
2. **Build the full source file list.** Run `git ls-files --cached --others --exclude-standard` (already sanity-checked as trustworthy in step 1) and write the result, one file path per line, to `.cache/recuperate/source-files.txt` — this is the single gitignore-respecting file list every task below scopes itself against, so no task re-derives it independently.
3. **Dispatch work via the `Agent` tool, launched in parallel.** For each unit of work (steps 4-9), call `Agent` using the complete content of its role's reference file (see Agent roles reference above) as the `prompt`, appending the concrete scope it needs — these are reference-defined roles, not registered subagent types, so leave `subagent_type` at its general-purpose default. Launch every unit of work that has no dependency on another's output in a single message with multiple `Agent` tool calls — this is what makes them run in parallel rather than staggered one after another; never launch independent units one at a time across separate messages.
   - **Terminology: every "Enqueue `<role>`" instruction in the steps below means exactly this — call `Agent` for that unit of work, using its role reference file's content as the prompt.** "Enqueue" is never a chat message or any mechanism beyond this one `Agent` call.
   - Each unit of work gets its own disjoint output path so parallel agents never race each other on a shared file, regardless of which one finishes first.
   - Agents don't talk to each other or hand back a summary beyond their own final message — each one's only expected output is a completion signal (`JOB DONE`) or a plain statement of why it couldn't finish (genuine hard failure). Retrieve actual results by reading each one's output path directly, never from its final message.
   - **Wait for every launched agent's result before treating that batch as done.** A batch with even one call still running, or one that returned partial output, is not a valid base for the next step — there's no time limit on this wait, and a slow agent is progress, not a hang. An agent interrupted partway through has not produced valid output; re-run it to completion rather than build on what it managed before being cut off.
   - **This skill has exactly one real dependency between units of work: `ticket-researcher` (step 9) on `git-explorer` (step 6)**, because each `ticket-researcher` batch's very scope — which ticket IDs to hand it — comes from reading `git-explorer`'s finished `ticket.md`. There's no dependency mechanism to declare for this; it's simply that `git-explorer`'s `Agent` call must return and `ticket.md` must be read before a `ticket-researcher` call can even be constructed, so those calls go in a later message, never the same one as `git-explorer`'s.
4. **Enqueue `domain-researcher` for each domain to study.** Determine the domain(s) to research from the project's own description (README, package/manifest) — never ask the user first; if no domain is clearly named, pick the most reasonable candidate(s) yourself (most prominent directory/module grouping, the subject of the README) and let `domain-researcher`'s own Scope section record that assumption. Enqueue one `domain-researcher` call per domain through the dispatch mechanism from step 3, each scoped to its own domain name.
5. **Enqueue `public-api-writer` for the whole project.** Unlike `domain-researcher`, this role takes no per-domain scope — enqueue a single call through the dispatch mechanism from step 3, covering the full project; the role's own workflow decides internally whether to split further across its own sub-workers.
6. **Enqueue `git-explorer` for the whole project.** Also no per-domain scope — enqueue a single call through the dispatch mechanism from step 3, covering the full project's git history. Its `ticket.md` output is a hard prerequisite for the later `ticket-researcher` calls in step 9, which must go in a later message, never the same one as this step.
7. **Enqueue `ext-lib-inspector` for the whole project.** Also no per-domain scope and no dependency on any other unit of work's output — enqueue a single call through the dispatch mechanism from step 3, alongside steps 4-6, covering the full project's manifests.
8. **Split `.cache/recuperate/source-files.txt` into 50-file chunks and enqueue one `logic-describer` call per chunk.** Read the file list from step 2 and partition it into consecutive groups of 50 paths each (the last group holding the remainder, whatever size that leaves it). For each chunk, enqueue a `logic-describer` call through the dispatch mechanism from step 3, passing that chunk's file paths inline in the prompt as its scope — never the whole `source-files.txt` path as a single call's scope, and never more than 50 files to one call. These calls have no dependency on any other unit of work's output, so they go in the same message as steps 4-7.
9. **Once `git-explorer`'s call from step 6 has returned, split `.cache/recuperate/git/ticket.md`'s ticket IDs into 50-ticket batches and enqueue one `ticket-researcher` call per batch.** This is a separate, later dispatch through the same mechanism from step 3 — never in the same message as step 6, since it depends on `git-explorer`'s `ticket.md`, which doesn't exist yet at that point. Read `ticket.md`, partition its ticket IDs into consecutive groups of 50 (the last group holding the remainder), and for each group enqueue a `ticket-researcher` call, passing that batch's ticket IDs inline in the prompt as its scope — mirroring step 8's chunking for `logic-describer`, and never more than 50 tickets to one call. If `git-explorer`'s call reported a hard failure instead of `JOB DONE` (no `ticket.md` produced), skip this step entirely and note why in the final report. If `ticket.md` reports zero tickets found, there's nothing to enqueue — also skip, with no batches created.
